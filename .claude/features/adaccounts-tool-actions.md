## Purpose
Owns the TKQC tool catalog (~17 functions modeled on the reference FB-automation tools), the temporary 4-group Panel 1 catalog, multi-selected workflow-step state, schema-driven Panel 2 step forms, run-control settings (Luồng/Delay), and selected-workflow runner flow. Selecting functions in Panel 1 appends them to Panel 2 in click order; each selected function becomes an expandable white path-card step with a green `Bước N` pill, 6-dot drag handle, right-side `X` remove action, and schema-driven form skin. The Panel 2 run button runs the selected steps over the selected accounts via the FB-over-extension API layer (apps/adaccounts/src/api/). 3 tools wired so far (rename, open-close-account, remove-user); the rest still show in the catalog but warn/disable truthfully when no runner exists. The form building blocks remain reusable by Page tools through per-panel tool-action instances.

## Flow
1. `TkqcFunctionPanel` resolves selected account rows from `useAccountList` + `useAccountSelection`, then renders `ToolPanel` as Function panel 1.
2. `ToolPanel` renders the redesigned `Kho chức năng` catalog: compact title-only header controls, compact search/actions row, plus the temporary 4 group labels `Super Share`, `Kháng TKQC`, `Đổi Info`, and `Xoá QTV ẩn` from `TOOL_UI_GROUPS`. Groups expand/collapse to show function rows. Rows support per-group drag reorder from the 6-dot handle and persist the UI order to localStorage; selected rows dim and show a green check, pinned rows show a green pin, and placeholder disabled rows dim and show a locked/permission marker until real auth rules are wired.
3. Clicking a function row calls `selectFunction(fn.id)` on the TKQC tool-actions instance. If the function is not already selected it is appended to `selectedFunctionIds`, preserving the user's click order. If it is already selected, Panel 2 focuses/expands that step. Panel 1 no longer renders switches or inline-expanded config forms.
4. `TkqcDetailPanel` resolves the same selected account rows for Function panel 2, then renders `ToolDetailPanel`.
5. `ToolDetailPanel` reads `selectedFunctions`, `expandedStepIds`, and `valuesFor(fn)` from the TKQC tool-actions instance. It renders each selected function as an ordered white path-card step through `ToolStepFrame`, with icon, runnable/unwired status text, 6-dot drag handle, green `Bước N` pill, right-side `X` remove action, and responsive `panel-two` field skin. The compact Panel 2 header shows `Quy trình - N bước` and no longer repeats selected-account count. Dragging a step calls workflow-only `reorderSelectedFunctions` and does not mutate the Panel 1 catalog order. Clicking a step expands/collapses its `ToolFunctionForm` fields (text/number/textarea/select/switch/file via shared-ui where applicable). Removing a step drops it from the workflow but keeps its form values in session.
6. Between workflow steps, Panel 2 shows a white `+ Giây Delay` chip by default; clicking it focuses a seconds input, then blur/Enter stores a per-connector delay in component memory (Escape clears that connector). These delays are not persisted and reset on page reload.
7. Panel 2 owns Luồng + Delay ms inputs via `use-tool-runner-settings`, plus footer actions. `Lưu Template` is visible but disabled until template persistence is scoped. `Chạy N bước/M tài khoản` uses `runBatch` with a per-account worker: each worker runs ALL selected steps sequentially for that account (applying per-connector step delay between steps), then waits `delayMs` before picking up the next account from the shared queue. Concurrency = `threads` (worker pool). Toast per step per account reports success/fail individually; successful `patch` values update account-list via `applyPatches`. Toasts via vue-sonner (`@mf2/shared-ui/sonner` toast); the `<Toaster>` outlet lives in AdAccountsPage.

## APIs used
- Facebook (via the SMIT Connect browser extension, never direct): Graph REST `graph.facebook.com/v24.0/act_<id>` (rename + remove-user context), Graph REST `GET /act_<id>/users/<uid>?method=DELETE` and BM fallback `GET /act_<id>/userpermissions?user=<uid>&method=DELETE&business=<bmId>` (remove-user), account-settings HTML scrape on adsmanager/business hosts (hidden admin detect), plus internal GraphQL `business`/`adsmanager`.facebook.com `/api/graphql/` (deactivate/reactivate doc_ids). Auth: access_token + fb_dtsg + lsd scraped from the Ads Manager page by fb-token. Token is the logged-in FB user's, not per-account.

## State
- orderedFunctions + expandedIds + enabledIds + per-tool values: module-scoped in the TKQC instance created by use-tool-actions. orderedFunctions seeds from localStorage `adaccounts.tool-order.v1`; enabledIds seeds from `adaccounts.tool-enabled.v1` for legacy compatibility; form values are stored per tool id so a selected tool keeps its config while the user switches rows.
- Panel 1 UI group row order: ToolGroupList persists per-group function order to localStorage `adaccounts.tool-ui-group-order.v1`; saved ids are filtered against the current catalog and new catalog functions append in source order.
- selectedFunctionIds + selectedFunctions: module-scoped in the TKQC instance. Panel 1 appends function ids in user click order; Panel 2 renders that ordered list as workflow steps. Panel 2 drag calls `reorderSelectedFunctions(nextIds)`, which reorders only selected ids and appends any missing selected id in prior order as a safety fallback; it does not write localStorage or change Panel 1 catalog/group order.
- selectedFunctionId: active/focused step id. Clicking an already-selected function in Panel 1 focuses and expands that step in Panel 2.
- expandedStepIds: Panel 2 step cards currently expanded for configuration.
- threads: module-scoped ref in use-tool-runner-settings, persisted to localStorage `adaccounts.tool-runner-settings.v1` (watcher).
- stepDelaySeconds: component-local map in `ToolDetailPanel`; each connector between workflow steps may have a separate seconds delay, not persisted and not shared across connectors.
- FB token bundle: in-memory module cache in fb-token.ts (1 user/session, not persisted). resetToken() drops it.
- selectedAccounts: resolved in [[adaccounts-tkqc-tab]] (selectedIds ∩ account-list data) and passed separately to ToolPanel and ToolDetailPanel wrappers — account-selection store still only holds ids (decoupled from account data).

## Decisions / Gotchas
- **FB calls go through the extension only:** api/smit-connect.ts proxies every FB request via chrome.runtime.sendMessage (cmd:'fetch') so cookies are borrowed + CORS bypassed. NEVER fetch graph.facebook.com directly. No extension installed → extFetch throws → each batch row reports the error, UI doesn't crash.
- **Token is the logged-in FB user's, not per-account:** fb-token scrapes access_token/fb_dtsg/lsd/user_id from the Ads Manager page once (in-memory cache). 1 user acts on many ad accounts. Ported from adscheck Facebook.js getFacebookToken type B. Regex is the fragile point — isolated in fb-token, fix one place.
- **act_ prefix vs bare id:** graph REST uses `/act_<id>` (rename); GraphQL mutations use the bare numeric id (open/close strip the act_ prefix). Easy to mix up.
- **Workflow-step run button:** TKQC now runs the selected workflow steps from Panel 2, not an enabled set from Panel 1. Panel 1 is a catalog; Panel 2 owns configuration + run action. Steps execute in the order the user selected functions in Panel 1. Only ids present in `TOOL_RUNNERS` (`rename`, `open-close-account`, `remove-user` currently wired) execute real runners; tools without a runner still warn `chưa được đấu API` rather than faking success.
- **Workflow-only Panel 2 reorder:** Panel 2 drag uses `reorderSelectedFunctions`, not catalog `reorder()`. It changes selected workflow order and therefore runner order, but keeps Panel 1 `ToolGroupList` order/localStorage unchanged.
- **Remove keeps values:** Panel 2 `X` removes the id from `selectedFunctionIds` and `expandedStepIds`, but does not clear `formValuesById`; reselecting the same function restores prior field values for the session.
- **runBatch never rejects:** every account yields a RowResult (errors included); bounded concurrency = Luồng, delay between launches = Delay (anti-rate-limit). The worker receives `(account, index)` — index = stable position in the selected list, so sequential tools number deterministically even under concurrency.
- **File fields are display-only until a runner contract is added:** ToolFunctionForm currently stores the selected file name, not the `File` object. Any future file-based runner must first extend the runner/value contract or pass files through a separate app-local map; do not assume `values` contains a `File`.
- **Shared run-control settings:** TKQC and Page panels intentionally share `useToolRunnerSettings` and localStorage key `adaccounts.tool-runner-settings.v1`; changing Luồng/Delay in one panel changes the other. Defaults: threads=2, delayMs=200.
- **Worker-per-account model:** `runBatch` worker runs ALL steps for one account before releasing. Step delay (`stepDelaySeconds`) is applied between steps within that account. `delayMs` (from settings input) is the inter-account delay after a worker finishes one account and before it picks up the next. This matches the queue/backlog model: fast accounts are picked up sooner, slow accounts don't block others.
- **Rename modes (2):** `random` → base + random number (110599–999999); `sequential` → base + incrementing number where the start = max existing `<base> <n>` + 1 (scanned from `ctx.allAccounts`, never below `startNum`), then `start + index` per account → deterministic + collision-free under concurrency. Accounts are picked by ticking rows in the table, so there is no per-account "id | name" input mode. Naming is a convenience only — Meta does NOT require unique account names, so there is no "duplicate name" error handling. A rename failing for missing BM-manage permission is reported as-is (no self-grant this version — user grants it manually).
- **Rename wildcard `*`:** if the base name contains `*`, the number replaces each `*` (e.g. `Shop * VN` → `Shop 837421 VN`); otherwise it's appended at the end; empty base → the number alone. Wildcard bases can't be scanned for sequential start (number isn't at the end) → they start from `startNum`.
- **Rename needs the full list:** sequential numbering reads existing account names via the runner's optional 4th arg `ctx.allAccounts` (passed by ToolPanel from `useAccountList`), NOT a fresh `/me/adaccounts` call — reuses the already-scanned list (saves one FB call). Other runners ignore `ctx`, like `index`.
- **Remove-user modes (5):** `hiddenOnly` deletes only detected hidden admins; `allExceptMe` deletes normal+hidden admins except current user+owner; `allExceptIdsAndMe` deletes normal+hidden admins except input keep-list; `byIdExceptMe` deletes input UIDs; `selfRemove` deletes only the current FB user id. UID textareas are newline-only (one UID per line), trim each line, and ignore lines that are not numeric IDs with at least 6 digits. The current FB user id from `getToken()` is protected in every bulk/input mode; `owner` from Graph is protected when present. `selfRemove` is the deliberate exception, but it is blocked locally when current user is the account owner because Meta returns (#100) for owner permission changes.
- **Remove-user account context:** before deleting, bulk/admin modes load `owner`, `owner_business`, `users`, and `userpermissions.limit(500)` via Graph v24.0; `selfRemove` uses a lighter context without `users` because it only needs owner + bmId fallback. The BM id used for fallback delete comes from the current user's `userpermissions` row, NOT from `owner_business.id`.
- **Remove-user hidden detect:** hidden admin detection does batch Graph diff first; only if counts differ (or batch diff fails) does it scrape account settings HTML from adsmanager/business host and parse `name:null` users. BM hidden-admin GraphQL doc_id flow is out of scope for TKQC remove-user.
- **Remove-user delete endpoint:** FB expects HTTP GET with query param `method=DELETE` for both `/act_<id>/users/<uid>` and `/act_<id>/userpermissions?user=<uid>&business=<bmId>`. Do NOT switch to HTTP DELETE unless verified live. The helper returns the method used (`users_delete` or `userpermissions_delete`) so self-remove and admin removal can report which fallback path succeeded. Each UID delete waits the same UI Delay value before the next UID inside the same TKQC.
- **Remove-user no local patch:** deleting admins changes permissions, not fields displayed in `AdAccount`, so the runner returns only a summary message and no `patch`.
- **Conditional fields via `showWhen`:** a ToolFieldSchema may set `showWhen: { key, equals }`; ToolFunctionForm hides it (v-show) until that field matches. Used to hide rename "Số bắt đầu" unless mode='sequential', and remove-user UID textareas unless their matching mode is selected.
- **doc_ids are FB-schema-fragile:** open=9984888131552276, close=9895135750555877 — break when FB rotates GraphQL schema (accepted risk, documented in the brainstorm report).
- **GraphQL errors arrive as `errors[]`:** FB returns mutation failures as an `errors[]` array, not `data.error` — fb-graph.graphql() checks both, else a failed mutation reads as success.
- **Auth-error retry:** graph()/graphql() detect auth errors (code 190/102/463/467 or token/session text), call resetToken(), and retry once with a fresh token — so a rotated fb_dtsg/access_token mid-session self-heals without a page reload.
- **Open-account success is unverified live:** `ADMARKET_ACCOUNT_STATUS_ACTIVE` marker + the open doc_id are from the brainstorm/docs, NOT confirmed against a real response. No marker + no error → reported as FAILURE (truthful-pessimistic) until verified on a live account.
- **Local list/cache update via patch (no re-fetch):** a runner returns `patch` = the fields it changed on success (rename → { name }, open → { status: 1 }, close → { status: 101 }); runBatch forwards it; ToolPanel maps successful patches by accountId and calls account-list `applyPatches`, which mutates the in-memory list + overwrites the extension cache. The status codes are the FB account_status values (1=Hoạt động, 101=Đóng) the table already maps. Wiring is generic — a new tool participates just by returning a `patch`; one that changes nothing simply omits it. Close uses 101 by decision; if FB actually returns 2 (Vô hiệu) after deactivate, change it in open-close-account.ts only.
- **Schema-driven form (DRY):** one ToolFunctionForm renders every function from its `fields` array — no hand-written panel per button. Add a function = add a catalog entry, not a component.
- **Panel 2 field skin is opt-in:** ToolFunctionForm keeps the default skin for other contexts and only applies the soft rounded TKQC Panel 2 field surface through `variant="panel-two"`. Prefer this prop over broad wrapper CSS so Page/other tool-action forms do not inherit TKQC-only visuals.
- **Temporary 4-group catalog:** TKQC Panel 1 uses `TOOL_UI_GROUPS` with product-approved temporary labels (`Super Share`, `Kháng TKQC`, `Đổi Info`, `Xoá QTV ẩn`). The mapping is intentionally easy to edit later; `TOOL_GROUPS` remains the source catalog and `TOOL_FUNCTIONS` remains the flat source for ordering/legacy consumers.
- **Panel 2 workflow steps, not inline expand:** clicking a TKQC function appends it to Panel 2 if not already selected, preserving click order. Clicking an existing function focuses/expands its step. `ToolFunctionForm` renders inside each expanded step. Do not reintroduce switches or inline-expanded forms into TKQC Panel 1 unless the product decision changes.
- Panel header chevrons own panel collapse for TKQC Function panel 1 and 2 through `useWorkspacePanels`; the shared workspace frame no longer renders separate floating close `X` buttons over the panel surface.
- **Order persistence merges, not replaces:** buildOrdered() keeps saved ids that still exist and appends new catalog functions — adding a tool later won't be hidden by a stale saved order.
- **Drag handles are siblings of expand buttons, not nested:** nesting an interactive handle inside a `<button>` is invalid HTML; Panel 1 and Panel 2 keep drag handles next to toggle buttons. Panel 2 uses the `.tool-step-drag-handle` class for vuedraggable.
- **vuedraggable needs two-way binding:** bind with `v-model` (computed getter/setter), NOT one-way `:model-value`+`@update:model-value`. One-way binding lets SortableJS reorder the DOM but the component re-reads the unchanged list and snaps back — drag appears broken. Panel 1 writes through catalog/group reorder; Panel 2 writes through `reorderSelectedFunctions`. (Matches the working pattern in shared-ui CustomColumn.vue.)
- **Delay chip between steps:** Panel 2 no longer shows a footer Delay input or a default `Delay 200ms` connector. Each connector shows `+ Giây Delay` by default. Clicking a connector edits that connector's own seconds delay in component memory; `runSelectedWorkflow` waits that delay after the preceding step finishes and before the next step starts. Connector delays are not persisted and reset on reload.
- **Reuses shared-ui form components:** ToolFunctionForm uses `Input/Textarea/Select/Switch/Label` from `@mf2/shared-ui/form-controls` / `@mf2/shared-ui` (shadcn-vue/reka-ui), not hand-rolled native inputs. Shared-ui `SelectContent`/`SelectItem` own the same soft green/gray palette as table header `DropdownMenu` options (`#F3F7F5`, `#5E6360`, `#D8E9E1`, `#BFD8CC`), so app code should not restyle every select dropdown locally.
- **Theme tokens required:** shadcn components consume CSS vars (`--input`, `--foreground`, `--primary`, `--ring`...). These are defined in `apps/adaccounts/src/styles.css` (mirrors `apps/shell/src/styles.css`) so the form renders correctly BOTH standalone (:3010) and inside the shell. If a shared-ui form component looks colourless, that token block is missing/out of sync.
- **Functions without fields:** activate-prepay, pay-debt, delete-card have no `fields`; their expanded form shows only a "không cần cấu hình" note (the shared "Bắt Đầu" button still runs them).
- **Icons constrained:** every group/function icon must be a shared-ui ICON_NAMES key, or the Icon component renders nothing.
